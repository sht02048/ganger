# 0208 개수 어긋남 바로잡기

## 배경

두 보고가 있다.

1. 0176 리뷰 뒤 남은 후속: 탭(또는 거르기)에 보이는 개수와 그 탭의 빈 목록 문구가 서로 맞지 않는 경우가 있다. Tickets의 보기·거르기 탭부터 확인하고 Runs·Dashboard의 같은 패턴도 본다.
2. 0189 워커가 데모 Dashboard에서 Done 개수가 서버 렌더 24, 브라우저 26으로 달라 React 수화 경고를 봤다. 시간 기준(최근 7일, 오늘 경계, 시간대)이 서버와 브라우저에서 다르게 계산되는 것으로 의심된다.

## 운영자 결정 (2026-11-24)

- 먼저 재현하고 원인을 PR 본문에 적는다(어느 화면·어느 계산).
- 개수와 목록·문구는 같은 계산 결과에서 나오게 한다.
- 서버와 브라우저가 같은 기준 시각·시간대로 계산하게 한다(서버가 정한 값을 그대로 쓰는 등).
- 화면 모양·문구는 바꾸지 않는다(틀린 값만 고친다).
- DB 변경 없음.

## 원인

### Dashboard·Stats·Runs 수화 어긋남

- 서버는 요청 쿠키 `tz`의 시간대로 화면을 그리고, 브라우저는 컴포넌트를 그릴 때마다 `document.cookie`의 `tz`를 다시 읽어 query key를 지었다.
- 루트의 시간대 맞추기(`TimeZoneSync`)가 브라우저 시간대로 쿠키를 바꾸는데, 느린 기기에서 화면 수화가 나뉘면 쿠키를 바꾼 뒤에 화면이 수화됐다. 그러면 화면은 다른 시간대의 key로 다시 읽고, 최근 7일 경계에 걸린 런 수가 달라 수화가 어긋났다.
- 데모(지금 UTC 23:47, 쿠키 Asia/Seoul, 브라우저 UTC, CPU 8배 느리게)에서 서버 렌더 Done 24, 브라우저 26과 `Hydration failed`를 재현했다. 쿠키와 브라우저 시간대를 바꿔 26→24도 재현했다.

### Tickets 탭 개수와 빈 목록 문구

- 탭 개수는 모든 티켓을 `matchesFilter`로 셌고, 묶기 보기 목록은 0176 결정 4대로 자기 런만 맞는 상위 이슈를 숨겼다.
- 그래서 상위 이슈 자기 런만 거르기에 맞으면 묶기 보기에서 탭 개수는 1인데 목록은 "이 조건에 맞는 티켓이 없어요."였다.
- Runs(검토 필요·전체)와 Dashboard 칸 개수는 목록과 같은 배열에서 세어 어긋나지 않았다.

## 고친 것

- Dashboard·Stats·Runs 로더가 쓴 시간대를 로더 결과로 돌려주고, 화면은 그 값으로 query key를 짓는다. 서버 렌더는 서버가 정한 시간대를 수화 때 그대로 쓰고, 쿠키가 바뀐 뒤에는 로더가 새 시간대로 미리 읽은 다음에 화면 key가 바뀐다.
- Tickets 탭 개수는 지금 보기의 목록과 같은 거르기로 센다. 모든 티켓 보기는 전과 같고, 묶기 보기는 보인 하위·따로 있는 티켓을 센다. 0176 결정 4의 "거르기 개수에는 남는다"는 모든 티켓 보기에만 남는다.
- 0044 브라우저 시험이 같은 날의 시각만 기대해, 자정 직후 CI에서 날짜가 붙은 시각을 못 찾았다(PR #264). 날짜가 붙어도 맞게 기대값을 고쳤다. 원인은 시험의 기대값이고 이 티켓의 시간대 원인과는 다르다.
