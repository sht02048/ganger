# 0194 모바일: 요청 번호·응답 잃은 쓰기 재전송·서버 호환 범위

## 배경

Orca 모바일 구조 비교(2026-11-23) 결과 운영자가 고른 개선이다.

- `apps/mobile/src/runs/request-ids.ts`가 요청 번호를 `Math.random`으로 만들었다.
- `isCompatibleServer`가 계약 버전이 같은지와 최소 서버 버전 0.4.0으로 판단해, 필드 하나만 더해도 옛 앱이 막혔다.
- 응답을 잃은 쓰기(네트워크 오류)는 실패로 보이고 다시 보내지 않았다.

## 운영자 결정 (2026-11-23)

1. 호환 범위: 서버 v1 응답 `meta`에 `contractVersion`(N)과 `minClientContractVersion`(M)을 싣는다. 앱은 자기 계약 K와 필요로 하는 최소 서버 계약 S를 갖는다. 호환은 N ≥ S 그리고 K ≥ M이다. 더하는 변경은 N만, 빼거나 뜻을 바꾸는 변경은 M도 올린다. 최소 서버 버전(0.4.0) 검사는 이 규칙으로 대신한다.
2. 맞지 않을 때: 앱이 오래됐으면 "앱을 업데이트해 주세요", 서버가 오래됐으면 "서버 맥의 Ganger를 업데이트해 주세요"를 보인다. 마지막 내용은 보이고 행동 버튼은 끈다.
3. 모르는 값: 앱의 응답 검사는 모르는 필드를 버리고, 모르는 상태·종류 enum 값은 "알 수 없는 상태"로 보이며 화면을 깨지 않는다.
4. 응답을 잃은 쓰기: 네트워크 오류면 버튼 자리에 "보냈는지 확인 중이에요" → 3초 뒤 같은 요청 번호로 한 번 더 → 그래도 응답이 없으면 "보냈는지 확인하지 못했어요"를 보이고 연결되는 대로 Dashboard를 다시 읽어 결과를 보인다. 서버가 분명히 거절하면 이유를 보이고 다시 보내지 않는다. 답하기, Human Check, 거절, 재개, 취소, 다시 맡기기, 이어서 맡기기 모두에 적용한다. 요청 번호는 `expo-crypto`의 `randomUUID`다.

## 구현 메모

- 이번 변경은 계약 번호를 1로 둔다. 이 규칙 전 앱은 계약이 정확히 1이어야 해서, N을 올리면 그 앱이 막힌다.
- 서버는 엄격한 스키마로 응답을 만들고, 앱은 `packages/api`의 `app*` 스키마로 읽는다. 서버가 잘못된 값을 `unknown`으로 흘려보내지 않게 하려는 것이다.
- 재개 전 상태 읽기가 실패하면 아직 보내지 않았으므로 다시 보내지 않고 지금처럼 실패로 보인다.
- 응답을 한 번 잃은 뒤 다시 보낸 요청이 서버 오류로 끝나면, 앞 요청이 닿았을 수 있어 "확인하지 못했어요"로 보인다.
- 확인하지 못한 시트는 저절로 닫지 않고 보내기를 잠근다. 읽기만 먼저 살아나면 안내가 보이기도 전에 시트가 닫히기 때문이다. Dashboard를 다시 읽으면 닫고 결과를 보라고 문장을 바꾼다.
