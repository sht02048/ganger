# 런은 대화형 에이전트를 Orca 오케스트레이션으로 맡겨 돌린다

런의 에이전트는 비대화형(`claude -p`처럼 한 번 실행하고 끝나는 모드)으로 띄우지 않는다. 대화형 에이전트를 러너의 Orca 오케스트레이션(`Task`와 `Dispatch`, `ask`/`reply`, `worker_done`)으로 맡긴다(운영자 결정 Q82 개정, 2026-11-17). 에이전트가 일하다 묻는 결정을 운영자가 이 오케스트레이터 화면에서 답하게 하려는 것이다. 에이전트의 질문 → 오케스트레이터가 받아 손댈 일에 보임 → 운영자가 답함 → 오케스트레이터가 ssh로 `reply` → 에이전트가 이어 감 → 에이전트의 완료 보고(`worker_done`)로 런이 끝난다. 이 흐름을 비대화형 ssh만으로 돌릴 수 있는지는 [research 0008](../research/0008-orca-orchestration-run.md)에서 확인했다.

- **런의 끝은 완료 보고다.** 대화형 에이전트는 일을 마쳐도 프로세스가 끝나지 않고 종료 코드도 없다([research 0004](../research/0004-orca-run-contract.md) 3절). 그래서 에이전트 결과는 종료 코드가 아니라 완료 보고의 outcome(성공, 실패)으로 정하고, 보고를 받으면 오케스트레이터가 에이전트를 닫는다. 보고 없이 에이전트가 사라지면 비정상 종료다([ADR 0004](0004-agent-merges-its-own-pr.md), GLOSSARY).
- **러너마다 우편함 터미널과 오래 쓰는 오케스트레이션 Run을 하나씩 둔다.** ssh 호출자는 Orca 터미널 밖이라 코디네이터 신원이 없다. 러너 어댑터가 에이전트 없는 터미널을 하나 자동으로 만들어 그 핸들을 신원으로 쓰고, 사라지면 다시 만든다. 오케스트레이션 Run은 러너마다 하나를 오래 쓰고, 지울 수 없는 Run·`Task` 기록은 쌓이게 둔다.
- **메일은 소비하지 않고 읽는다.** `inbox --terminal run:<runId> --full`을 최신 순 창으로 읽고(창은 런의 Task 시작 앞 메일이 들어올 때까지 200 → 800 → 3200행), 메일을 처리했는지(질문에 답했는지 포함)는 오케스트레이터 DB가 기준이다. 읽음 처리(ack)도 지우기도 하지 않는다. Orca에는 메일 하나만 처리됨으로 바꾸거나 지우는 명령이 없고, 소비하는 `check`는 가장 오래된 묶음 전체를, `reset --messages`는 Run의 메일 전부를 바꾼다. `inbox`는 읽음 여부와 상관없이 메일을 주므로 읽음 처리해도 읽는 양이 줄지 않는다. 처음에는 `check --peek`으로 읽었으나, 안 읽은 메일을 오래된 것부터 100개만 줘서 쌓인 메일 뒤의 새 질문을 놓쳤다(티켓 [0231](../tickets/0231-orca-mailbox-backlog.md)에서 바꿈, 2026-11-25). 한 러너의 런들은 같은 Orca Run을 쓰므로 한 폴링 주기에 Run마다 한 번만 읽어 나눠 쓴다(티켓 [0232](../tickets/0232-orca-mail-once-per-poll.md)).
- **권한은 미리 허용한다.** ssh로는 권한 프롬프트를 거절만 할 수 있고 허용은 러너 화면에서 사람만 한다. 그래서 각 프로젝트의 에이전트 설정에서 필요한 권한을 미리 허용하도록 권하고 온보딩에서 안내한다. 오케스트레이터는 권한 전체 우회를 쓰지 않는다. 권한 대기가 생기면 화면은 "러너 화면에서 허용해 주세요"를 안내하고 거절만 둔다.

## Consequences

`worker-start`에는 `--branch`가 없어 Orca가 러너의 접두사를 붙인 브랜치를 만든다. 오케스트레이터는 시작할 때 실제 브랜치 이름을 받아 DB에 저장하고, PR은 그 이름으로 먼저 찾는다(Q40의 1순위 규칙을 고친 것, 2순위 티켓 키 검색은 그대로). 결정적 워크트리 이름(`--name`)은 시작 멱등 키로 계속 쓴다.

질문과 답은 ssh 명령 인자로 오간다. 답 본문은 research 0004의 인자 인용 규칙과 길이 한계를 따른다.

[research 0007](../research/0007-headless-agent-run.md)의 비대화형 방식은 채택하지 않았다. 그 문서는 근거 기록으로만 남는다.

## Considered Options

- **비대화형 `-p`로 띄우기(research 0007)**: 종료 코드로 끝과 결과를 깔끔하게 얻지만, 권한 질문이 거절로 끝나 Waiting for Input이 거의 오지 않고 에이전트가 운영자에게 물을 길이 없다. 운영자가 오케스트레이터 화면에서 에이전트 질문에 답하려는 목적을 이루지 못해 기각했다.
- **대화형으로 띄우고 에이전트가 `done`인 채 N분 지나면 끝으로 보기**: 에이전트가 쉬는 것과 질문하고 기다리는 것, 일을 마친 것을 가를 수 없고 N을 정할 근거가 없다. 결과도 성공·실패를 알 수 없어 기각했다.
