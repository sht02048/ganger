# Configuration

## Installation folder

The CLI keeps its files in one installation folder: `~/.ganger` by default, or the folder in `--home <dir>` or the `GANGER_HOME` environment variable.

## `.env`

`.env` holds only the minimum values needed to boot: port, bind address, data path, and encryption key. `ganger init` writes it, as described below. The addresses that other devices and your tracker use are set in Settings, as described in [Open it from other devices](networking.md#open-it-from-other-devices).

## `init` and `start`

- `init` writes `<home>/.env` (readable only by you) with the bind address `127.0.0.1`, port `3000`, the database `<home>/data/ganger.db`, and a newly generated encryption key. Change them with `--host`, `--port`, and `--database-path`, or edit the file later. If `.env` already exists, `init` leaves it unchanged, so the encryption key never changes by accident. If you lose or change the key, you have to enter the tokens again.
- `start` holds a lock file, `<home>/server.lock`, while it runs, so only one `start` (one web server and one worker) runs per installation folder. A second `start` for the same folder exits with an error. A lock left behind by a process that no longer exists is taken over.
- `start` reads `<home>/.env`. Shell environment variables with the same names (`WEB_HOST`, `WEB_PORT`, `DATABASE_PATH`, `ENCRYPTION_KEY`) override it. It applies pending database migrations, starts the web server and the worker, and prints the web address once it responds. If either process exits, `start` stops the other one and exits with an error, so a service manager can restart both. `SIGINT` or `SIGTERM` stops both.
- After an upgrade, run `start` again (or restart the service). It applies new migrations before anything else starts.

## Environment variables

| Variable            | Default                                                 | What it sets                            |
| ------------------- | ------------------------------------------------------- | --------------------------------------- |
| `GANGER_HOME`       | `~/.ganger`                                             | Installation folder (same as `--home`)  |
| `WEB_HOST`          | `127.0.0.1`                                             | Bind address                            |
| `WEB_PORT`          | `3000`                                                  | Port                                    |
| `DATABASE_PATH`     | Written by `init` as `<home>/data/ganger.db` (required) | SQLite database file                    |
| `ENCRYPTION_KEY`    | Generated by `init`                                     | Key that encrypts stored tokens         |
| `GANGER_LOG_LEVEL`  | `info`                                                  | Server log level                        |
| `GANGER_LOG_MAX_MB` | `10`                                                    | Size at which a server log file rotates |
| `GANGER_LOG_FILES`  | `5`                                                     | Rotated server log files to keep        |
| `GANGER_GH_CLI`     | `gh` on `PATH`, then Homebrew and `/usr/bin`            | GitHub CLI used for GitHub access       |

Mobile push goes through Expo Push only after a device turns on notifications. The worker sends to `https://exp.host/--/api/v2/push` by default. To use a different relay, set `GANGER_EXPO_PUSH_URL` in the environment of the process that runs `start`.

`start` reads only `WEB_HOST`, `WEB_PORT`, `DATABASE_PATH`, and `ENCRYPTION_KEY` from `.env`. Set the `GANGER_LOG_*` variables in the environment of the process that runs `start`; a line for them in `.env` has no effect. A launchd or systemd service does not inherit your shell's variables and gets only `PATH`, so add them to the service file. For detailed logs without any variable, turn on **자세한 서버 로그** (detailed server logs) in Settings > **서버 로그와 진단** (server logs and diagnostics).

## GitHub access

Ganger reads pull requests and merges them from the Dashboard with the GitHub CLI (`gh`) login of the user that runs the server, the same way Orca uses it. A token pasted in Settings is the fallback.

1. Install `gh` on the machine that runs the server (`brew install gh` on macOS, or see [cli.github.com](https://cli.github.com/)).
2. Log in as the user that runs `start` or the service: `gh auth login`. To use more than one account, for example a work and a personal account, run `gh auth login` once per account. Using several accounts needs `gh` 2.40 or later; an older `gh` uses only the active account.
3. In onboarding step 2 or Settings > **연결** (connections) > **GitHub**, choose **다시 확인** (check again), or **이 로그인으로 연결** (connect with this login) in onboarding.

For each repository, Ganger picks the first logged-in account that can see it, starting with the active account, and remembers the choice for a while. It uses the pasted token only when `gh` is not installed, no account is logged in, or no account can see the repository. When the chosen account cannot merge, the merge button stays off; Ganger does not switch to the pasted token for the merge. A pasted token needs Pull requests read access to read pull requests (Actions read shows CI state), and Pull requests and Contents write access to merge.

A launchd or systemd service runs as its own user with only `PATH`. Log in to `gh` as that user, or set `GANGER_GH_CLI` to the `gh` binary if it is not on that `PATH`. Ganger never stores the `gh` token and never shows it in the app, logs, or MCP responses.

## Ticket state after a merge

Ganger can move a ticket to a tracker state you choose when the run's pull request is merged. Open a tracker project under Settings > **프로젝트** (projects), then pick the state in **PR이 머지되면 바꿀 상태** (state to set when the PR is merged) under **트래커 티켓 상태** (tracker ticket state). The default is **바꾸지 않음** (don't change).

This setting is optional and meant for projects without the Linear–GitHub integration. If that integration already moves your tickets, leave the default. Ganger changes the state at most once per run, and leaves it alone when a pull request is closed without merging or a run has no pull request.

## Sleep

On macOS, `start` keeps the Mac from going to sleep while you are away (idle sleep) for as long as it runs, so runs keep going and webhooks still arrive. It holds the assertion with `caffeinate`, which you can see in `pmset -g assertions`, and releases it when `start` exits. If `caffeinate` fails, `start` prints a warning and keeps running. Turn it off with **서버가 도는 동안 이 맥이 잠들지 않게** (keep this Mac awake while the server runs) in Settings > **이 서버** (this server) (stored in `<home>/power.json`); the change applies within a few seconds without a restart. On Linux, `start` does not prevent sleep.

It cannot stop every kind of sleep. A laptop still sleeps when you close the lid, choose Sleep yourself, or run low on battery. To keep a laptop server awake with the lid closed, connect power and an external display (clamshell mode), or change the sleep settings with `pmset`. The same applies to runner Macs, which the orchestrator does not keep awake.
