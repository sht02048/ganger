# 에이전트 제어 스펙

운영자가 런의 에이전트에게 무엇을 보내고 어떻게 이어 갈지 정하는 기준 문서다. 2026-11-21 시안 승인과 같은 날 운영자 결정 C0~C7을 한곳에 묶는다. C0~C7은 2절에 운영자가 정한 문장 그대로 두었다. 본문은 그 결정을 코드 위치에 맞춰 풀어 쓴 것이고 새 결정을 만들지 않는다.

함께 쓴 ADR은 [0023](../adr/0023-human-check-request.md)(Human Check 요청을 `decision_gate`로 받기)다. 이 문서를 쪼갠 티켓은 [0146](../tickets/0146-workspace-brief.md)~[0150](../tickets/0150-pr-checks-info.md)이다. 용어는 [GLOSSARY](../../GLOSSARY.md)를 따른다. 시안은 아티팩트 "Ganger Agent Control"이고 색·간격은 참고일 뿐, 구현은 `packages/ui`의 토큰과 컴포넌트를 쓴다.

## 1. 배경

0.2.0 운영에서 런 DEE-12의 에이전트가 커밋만 하고 push·PR 없이 성공 보고를 했다(스펙 [0005](0005-run-outcome.md) R7). 에이전트는 티켓 내용과 Ganger와 주고받는 법만 받으므로, 작업을 어떻게 끝낼지(push, PR, 검사)는 프로젝트 규칙에 적혀 있어야 했다. 프로젝트 규칙이 없는 저장소나, 운영자가 Workspace마다 늘 덧붙이고 싶은 말이 있을 때 운영자가 쓸 자리가 없었다. 또 런이 끝난 뒤 남은 일을 같은 워크트리에서 이어 맡길 길, 도는 런에 말을 보낼 길, 사람이 확인해야 끝나는 일을 에이전트가 요청할 길, PR의 CI·충돌을 런 곁에서 볼 길이 없었다.

## 2. 운영자 결정(2026-11-21, 시안 승인)

- C0 원칙: Ganger 기본 지시서는 티켓 내용 + Ganger 와 주고받는 법(통신 규약)만 담는다. PR·시험 같은 작업 방식은 프로젝트 규칙이 정하고, 운영자가 원하면 Workspace 의 앞뒤 지시로 덧붙인다(기본 비어 있음).
- C1 앞뒤 지시는 Workspace 별(티켓 앞, 티켓 뒤 두 칸).
- C2 Settings › Workspace 에서 여러 줄로 편집, 옆에 "에이전트가 받을 지시서" 미리 보기(예시 티켓으로 합친 전체: 앞 지시 → 티켓 → 뒤 지시 → 통신 규약). 저장하면 새로 시작하는 런부터 적용. Run 상세에 그 런이 실제로 받은 지시서 전체를 보인다(그래서 런마다 보낸 지시서를 저장).
- C3 Human Check 요청: 통신 규약(ASK_GUIDE)에 "사람이 확인해야 끝나는 일은 decision_gate 로 무엇을 확인할지와 링크를 보내고 답을 기다린다"를 더한다. Ganger 는 이를 Waiting for Input · Human Check 로 보이고 To do·알림에서 Question 과 따로 묶는다("확인해 주세요", 청록). 무엇을 요청할지는 프로젝트 규칙·앞뒤 지시가 정한다.
- C4 Human Check 답: "확인했어요" / "고쳐 주세요" + 선택적으로 함께 보낼 말. 답은 그 런의 에이전트에게 가고 런은 Running 으로. Ganger 는 머지하지 않는다.
- C5 이어서 맡기기: 워크트리가 남은 끝난 런에서 새 런을 같은 러너·워크트리·브랜치로 시작("런 #n 을 이어서" 연결). 지시서 = 운영자의 말 + 이전 런 보고 + 앞뒤 지시 + 통신 규약. 워크트리가 지워졌으면 같은 브랜치로 새 워크트리, 브랜치도 없으면 처음부터.
  - C5-1 이전 에이전트가 아직 살아 있으면: **이어서 맡기기를 막는다.** 버튼(과 MCP 쓰기가 있다면 그것)을 쓸 수 없게 하고 이유("이전 에이전트가 아직 떠 있어요 · 먼저 멈춰 주세요")와 멈추기 길을 보인다. Ganger 가 이전 에이전트를 자동으로 멈추거나 입양하는 코드는 빼고, 시작 직전에 다시 확인해 살아 있으면 시작하지 않고 같은 이유로 실패를 보인다. 살아 있는지 확인하지 못하면(러너 못 닿음) 막는다.
  - C5-2 워크트리·브랜치 찾기: 러너 저장소의 **로컬 브랜치 → origin 의 같은 이름 브랜치** 두 곳만. 둘 다 없으면 "브랜치가 없어 처음부터 맡겨요"로 처음부터. push remote·다른 remote·태그 충돌·단일 브랜치 clone 등을 위한 별도 처리는 빼서 단순하게(브랜치는 전체 ref `refs/heads/…`, `refs/remotes/origin/…` 로 읽는 정도는 둔다).
  - C5-3 시작 결과를 모를 때: 일반 런 시작의 복구 규칙을 그대로 쓴다. 이어서 맡기기 전용 복구 규칙은 두지 않는다(이어서 맡기기 = 시작 위치만 다른 런 시작).
  - C5-4 PR 은 브랜치를 따라간다: 같은 브랜치의 **열린** PR 은 새 런이 이어받고 이전 런에는 "다음 런으로 넘겼어요". 이미 닫히거나 머지된 PR 은 이전 런에 남는다.
- C6 에이전트에게 보내기: Running·Waiting for Input·Paused 런의 Run 상세 입력칸, Orca `send --to dispatch:` 로 보내고 타임라인에 "운영자가 보냄"으로 남긴다. 여러 런에 한꺼번에는 하지 않는다.
- C7 PR 정보: PR 을 읽을 때 CI 결과(statusCheckRollup)·충돌(mergeable)·base 보다 뒤처짐을 함께 읽어 Runs 행과 Run 상세 PR 구역에 작은 표시로. 런 결과는 바꾸지 않는다(0005 R1). 읽는 주기는 0144 의 PR 다시 읽기. CI 다시 돌리기 버튼은 넣지 않는다(운영자가 뺌).

## 3. 목표와 완료 기준

목표: 에이전트가 받는 지시서를 운영자가 보고 정할 수 있고, 런이 받은 지시서가 남는다. 사람이 확인해야 끝나는 일은 에이전트가 요청하고 운영자가 To do에서 답한다. 운영자는 도는 런에 말을 보내고, 끝난 런은 같은 워크트리에서 이어 맡긴다. PR의 CI·충돌·뒤처짐은 런 결과를 바꾸지 않고 곁에 보인다.

완료 기준(티켓마다 자세히 적는다):

- 0146(C0·C1·C2): Workspace에 앞뒤 지시를 저장하고, worker가 런을 시작할 때 앞 지시 → 티켓 → 뒤 지시 → 통신 규약으로 합친 지시서를 보내며 그 런에 저장한다. Settings › Workspace에서 편집하고 미리 본다. Run 상세에 받은 지시서가 보인다. MCP `get_settings`·`get_run`이 이를 읽는다.
- 0147(C6): Running·Waiting for Input·Paused 런의 Run 상세에서 에이전트에게 말을 보내고 타임라인에 "운영자가 보냄"이 남는다.
- 0148(C3·C4): 에이전트의 `decision_gate`가 Waiting for Input · Human Check가 되고, To do·알림에서 Question과 따로 묶이며, "확인했어요"·"고쳐 주세요"로 답한다.
- 0149(C5): 워크트리가 남은 끝난 런에서 "이어서 맡기기"로 같은 러너·워크트리·브랜치에 새 런을 시작한다.
- 0150(C7): Runs 행과 Run 상세 PR 구역에 CI·충돌·뒤처짐 표시가 붙는다.

## 4. 지시서(C0·C1·C2, 0146)

- 합치는 곳은 `packages/core/src/agent-brief.ts` 한 곳이다. 순서는 앞 지시 → 티켓 → 뒤 지시 → 통신 규약이고, 칸마다 앞뒤 빈 줄을 다듬은 뒤 빈 칸은 뺀다. 칸 사이는 빈 줄 하나다.
- 통신 규약은 러너 어댑터가 정한다(`Runner.agentProtocol`). Orca 러너는 `packages/runner-orca/src/agent-brief.ts`의 `ASK_GUIDE`를 낸다. 지시서를 합치는 일은 worker가 하고, 러너 어댑터는 받은 지시서를 그대로 stdin으로 넘긴다.
- 앞뒤 지시는 `workspaces.brief_before`·`brief_after`(빈 문자열 기본)에 둔다. 각 칸은 8,000자(유니코드 문자 수)까지이고 경계(web 서버 함수)에서 zod로 검사한다. 저장할 때 앞뒤 빈 줄을 다듬는다. 이름·최대 실행 시간 저장(`saveWorkspace`)은 앞뒤 지시를 건드리지 않는다.
- 런이 받은 지시서는 worker가 시작 명령을 보내기 직전(`recordStartRequested`)에 `runs.agent_brief`에 적는다. 시작 명령이 확실히 실패해 다시 보낼 때는 그때의 Workspace 지시로 다시 합쳐 다시 적는다. 이미 시작한 런은 Workspace 지시를 바꿔도 그대로다. 재개할 때 새 에이전트 세션을 띄우면(티켓 0118) 그 런이 받은 지시서를 다시 보낸다.
- Settings › Workspace: "에이전트에게 보내는 지시" 줄(ⓘ 툴팁, 요약 "티켓 앞 n줄 · 티켓 뒤 n줄")에서 바꾸기를 누르면 두 칸과 미리 보기가 펼쳐진다. 미리 보기는 예시 티켓으로 합친 전체를 칸 이름과 함께 보인다. 저장 문구 옆에 "새로 시작하는 런부터 적용해요"를 둔다.
- Run 상세: "받은 지시서"를 접어서 보인다. 지시서를 보내기 전인 런(Queued)과 이 기능 전에 시작한 런에는 없다.
- MCP: `get_settings`의 Workspace 일반 설정에 앞뒤 지시(`brief`)와 통신 규약(`agentProtocol`)을, `get_run`에 받은 지시서(`brief`)를 보인다. 앞뒤 지시와 받은 지시서는 다른 에이전트를 위한 지시이고 받은 지시서에는 트래커의 글이 들어 있어 `external` 칸에 둔다. 쓰기 도구는 더하지 않는다.

## 5. Human Check 요청(C3·C4, 0148)

- 통신 규약에 "사람이 확인해야 끝나는 일은 `decision_gate`로 무엇을 확인할지와 링크를 보내고 답을 기다린다"를 더한다. Orca 러너는 이 메시지를 Question(`ask`)과 다른 종류로 읽는다([ADR 0023](../adr/0023-human-check-request.md)).
- 런 상태는 Waiting for Input이고 종류는 Human Check다. To do·알림 사건에서 Question과 따로 묶고("확인해 주세요"), 색은 청록이다(ADR 0010을 0148에서 고친다). 최대 실행 시간은 다른 Waiting for Input처럼 흐른다.
- 답은 "확인했어요" / "고쳐 주세요" 둘에 함께 보낼 말(선택)을 붙인다. 답은 그 런의 에이전트에게 가고 런은 Running으로 돌아간다. Ganger는 머지하지 않는다.
- 0145에서 요약 결과 이름에서 뺀 Human Check가 이 종류로 돌아온다. 요약 결과가 아니다.

## 6. 에이전트에게 보내기(C6, 0147)

- Running·Waiting for Input·Paused 런의 Run 상세에 입력칸과 보내기를 둔다. web은 요청을 DB에 적고 worker가 러너 어댑터로 Orca `send --to dispatch:<id>`를 부른다. 결과를 타임라인에 "운영자가 보냄"과 보낸 말로 남긴다.
- Paused 런에 보낸 말은 런을 재개하지 않는다. 요청 표에 두고 "재개하면 전해요"로 보이며, 재개한 직후 worker가 보낸다(운영자 결정 2026-11-21, 0147). 멈춘 에이전트의 터미널은 살아 있어 바로 보내면 Paused인데 에이전트가 움직일 수 있다.
- Waiting for Input 런에 보낸 말은 바로 보내지만 질문의 답으로 다루지 않는다. 질문은 열린 채로 두고 답은 기존 답하기로만 한다(운영자 결정 2026-11-21, 0147).
- 한 번 보내기를 시작한 말은 다시 보내지 않는다. 결과를 모르면 "전해졌는지 확인하지 못했어요"로 남기고 운영자가 다시 보낼지 정한다.
- 여러 런에 한꺼번에 보내지 않는다. MCP 쓰기 도구는 더하지 않는다.

## 7. 이어서 맡기기(C5, 0149)

- 워크트리가 남은 끝난 런의 Run 상세에 "이어서 맡기기"를 둔다. 새 런을 같은 러너·워크트리·브랜치로 시작하고, 두 런을 "런 #n을 이어서"로 잇는다.
- 지시서는 운영자의 말 → 이전 런 보고 → 앞 지시 → 뒤 지시 → 통신 규약 순서다. 4절의 합치기를 넓혀 같은 곳에서 만든다. 처음부터 시작할 때만 앞 지시와 뒤 지시 사이에 티켓을 넣는다.
- 새 런은 `runs.continued_from_run_id`로 이전 런을 가리키고, 운영자의 말(`continue_message`)과 이어 받은 곳(`continue_place`: `same-worktree`, `recreated`, `from-scratch`)을 둔다. 새 런이 대기 중이거나 시작했으면 워크트리는 새 런의 것이라 이전 런이 지우지 못하고 Runners의 남은 워크트리에도 보이지 않는다.
- 새 런은 이전 런의 러너에 고정한다. 러너가 Offline이거나 자리가 없거나 사용량 한도에 닿으면 Queued로 기다리고 다른 러너로 옮기지 않는다.
- C5-1: worker가 이어 맡길 수 있는 끝난 런의 에이전트가 살아 있는지 읽어 `runs.agent_check`(`gone`, `alive`, `unknown`)에 적는다. `gone`일 때만 이어서 맡길 수 있다. 이전 에이전트는 운영자가 "이전 에이전트 멈추기"를 눌렀을 때(`agent_stop_requested_at`)만 멈춘다. 시작 직전에 다시 읽어 살아 있으면 시작하지 않고 같은 이유로 끝낸다.
- C5-2: 워크트리가 없으면 로컬 브랜치, 그다음 origin의 같은 이름 브랜치로 같은 경로에 `git worktree add` 한다. Orca `worktree create --branch`는 이미 있는 브랜치에 다른 이름을 붙이기 때문이다. Orca가 이렇게 만든 워크트리에 저장소 설정 훅을 돌리지 않으므로, 어댑터가 Orca와 같은 규칙으로 setup 명령을 정해 에이전트 시작 전에 돌린다. 실패하거나 결과를 모르면 그 런은 시작할 수 없음으로 끝나고, 워크트리가 남아 있어 다시 만들지 않았으면 돌리지 않는다(티켓 0155). origin을 읽지 못하면 처음부터 시작하지 않고 시작 실패로 다룬다.
- C5-3: 시작 결과를 모르면 일반 런처럼 워크트리의 에이전트를 찾는다. 시작 위치만 이름 대신 이어 받은 워크트리이고, 그 워크트리의 최신 에이전트가 이전 런의 것이면 시작하지 않은 것으로 본다.
- C5-4: 새 런이 시작하기 전에 머지되거나 닫힌 PR은 새 런의 PR 상태로 삼지 않는다. 새 런이 시작할 때까지는 이전 런이 PR을 계속 읽어 그 사이의 머지·닫힘을 이전 런에 남긴다. 새 런이 시작한 뒤 열린 PR은 새 런이 이어받고, 이전 런은 Run 상세에 "다음 런으로 넘겼어요"를 보인다.

## 8. PR 정보(C7, 0150)

- PR을 읽을 때 CI 결과(`statusCheckRollup`), 충돌(`mergeable`), base보다 뒤처진 커밋 수를 함께 읽는다. 읽는 주기는 0144의 PR 다시 읽기를 따른다.
- Runs 행과 Run 상세 PR 구역에 작은 표시로 보인다. 요약 결과는 바꾸지 않는다(스펙 0005 R1). CI 다시 돌리기 버튼은 넣지 않는다.
- Dashboard 카드의 칩 줄에도 PR 칩으로 보인다(운영자 결정 2026-11-21, 티켓 0167). PR이 Open일 때만 CI 실패 → 충돌 → base N커밋 뒤 순서로 두 개까지 보이고 나머지는 `+N`으로 묶는다. 선행 티켓 칩이 먼저 온다. PR을 못 읽은 런은 칩 대신 바닥 줄에 "PR 못 읽음"을 쓴다.

## 9. 티켓 나눔과 순서

- 0146(이 스펙의 첫 PR): 스펙·ADR·GLOSSARY·티켓 문서와 C0·C1·C2 구현.
- 0147·0148·0150: 0146 뒤. Run 상세와 지시서·통신 규약 코드를 함께 건드려 0146이 머지된 뒤에 한다. 서로는 Run 상세 파일이 겹칠 수 있어, 함께 돌리면 병합할 때 맞춘다.
- 0149: 0146 뒤. 4절의 지시서 합치기를 넓힌다.

## 10. 위험

- 마이그레이션은 one-way다(0146). `workspaces`에 두 열, `runs`에 한 열을 더한다(`ALTER TABLE ADD`). 옛 버전은 새 마이그레이션이 적힌 DB를 다운그레이드로 거부한다. 되돌리려면 이 버전 전의 DB 백업으로 돌아가야 한다.
- 0149 마이그레이션도 one-way다. `runs`에 다섯 열과 인덱스 하나를 더한다(`ALTER TABLE ADD`, `CREATE INDEX`). 되돌리려면 이 버전 전의 DB 백업으로 돌아가야 한다.
- 받은 지시서는 런마다 저장되므로 앞뒤 지시가 길면 DB가 그만큼 커진다. 칸마다 8,000자로 막는다.
- 앞뒤 지시는 모든 런의 에이전트가 읽는 지시라, 운영자가 잘못 쓰면 그 Workspace의 새 런이 모두 따라간다. 미리 보기와 "새로 시작하는 런부터 적용해요"로 알린다. 도는 런은 그대로다.
- 통신 규약을 worker가 합치게 바꿔, 러너 어댑터가 지시서에 무엇을 덧붙이지 않는다. 새 러너 어댑터는 `agentProtocol`을 내야 한다.
- `decision_gate`를 받는 Orca 쪽 동작(0148)은 스파이크로 확인한 뒤 쓴다. 확인 전에는 통신 규약에 그 문장을 넣지 않는다.
