# 모바일 클라이언트 스펙

모바일 클라이언트 구현의 기준 문서다. 조사 결과(research [0014](../research/0014-mobile-client.md))와 2026-11-19 운영자 결정 M1~M21, 데스크톱 알림 개선(티켓 [0103](../tickets/0103-desktop-notifications.md))이 만든 알림 사건, 그리고 이 문서와 함께 쓴 ADR [0015](../adr/0015-device-token-pairing.md)·[0016](../adr/0016-mobile-push-via-expo.md)을 한곳에 묶는다. M1~M21은 이 문서에 처음 모아 적는 결정이고(M5와 M14는 티켓 0103의 결정을 모바일에도 그대로 쓰는 것이다), 본문의 해당 문장이 그 결정이다(M2는 ADR 0015에, M10~M17은 ADR 0016에도 적었다). 이 문서는 새 결정을 만들지 않는다. 근거 문서에 없는 것은 「열린 질문」에 남긴다.

**갱신(2026-11-23, 티켓 [0188](../tickets/0188-mobile-plan-refresh.md)).** 계획을 쓴 뒤 0113~0183이 머지되고 v0.4.0이 나와 도메인과 화면이 바뀌었다. 본문의 사실을 지금 코드에 맞추고, 그날 운영자가 정한 M22~M45를 11절에 더했다.

용어는 [GLOSSARY](../../GLOSSARY.md)를 따른다. 문장 안에서 To do는 처리할 일로 쓴다. 이 문서를 쪼갠 티켓은 [0104](../tickets/0104-device-pairing-v1.md)~[0112](../tickets/0112-mobile-testflight.md)이고, 남은 열린 질문은 12절에 적은 티켓에서 푼다.

## 1. 목표와 완료 기준

목표: 운영자가 Mac 앞에 없을 때도 폰에서 처리할 일을 알림으로 받고, 답하기·거절·다시 맡기기로 런을 다시 움직이게 한다. 폰에 오는 이유는 거의 알림이다(research 0014 6절).

완료 기준:

- Ganger 화면에서 보인 QR로 iPhone을 이 서버에 연결하고, 앱에서 Dashboard의 세 칸(Queued, Running, Done)과 Runners를 본다.
- Question 알림을 눌러 답하기 시트에서 답을 보내면 그 런이 다시 Running이 된다. Human Check도 같은 시트 방식으로 "확인했어요" 또는 "고쳐 주세요"와 덧붙일 말을 보내면 Running이 된다(M22). Permission 거절, Paused 런 재개(M24), 런 취소도 앱에서 된다. 취소는 확인 시트를 거친다. Failed 카드에서 이전 런과 같은 저장소·러너·에이전트로 다시 맡기고, 워크트리가 남았으면 이어서 맡기기도 고를 수 있다. 둘 다 확인 시트를 거친다(M3, M38).
- 연결한 기기를 지우면 그 기기의 `/api/v1` 요청은 거절되고 그 기기로 가는 푸시도 멈춘다. 웹 화면은 여전히 인증이 없어, 그 기기가 서버 주소에 닿는 네트워크(Tailscale을 쓰면 tailnet)에서 빠지기 전까지는 웹으로 쓸 수 있다(8절).
- 서버 없이 앱 안 데모 모드로 모든 화면을 본다.
- iOS 앱을 TestFlight로 배포한다.

## 2. 범위와 제외

범위:

- **UI는 모바일용으로 따로 만든다(M1).** Ganger 웹 화면을 가져가지 않는다. 낱말과 상태 이름·색, 브랜드(Ink, Paper, Ganger Yellow, 호루라기 마크, 마스코트 규칙)는 웹과 같다([브랜드 가이드](../../packages/ui/brand/README.md), ADR 0010).
- **할 수 있는 일(M3, M22, M24).** 보기, Question 답하기, Human Check 답하기, Permission 거절, Paused 런 재개, 다시 맡기기, 이어서 맡기기, 런 취소. 다시 맡기기, 이어서 맡기기, 취소는 확인 시트를 거친다. Permission 허용은 웹과 같이 러너의 Orca에서만 한다(ADR 0009). 다시 맡기기와 할당은 지금 서버 규칙(`packages/db`의 `assignRun`, `active-run` 거절)처럼 끝나지 않은 런이 없는 티켓에만 된다. 그래서 다시 맡기기는 Failed 런에만 두고, Disconnected 런에는 두지 않는다(웹 Dashboard와 같다). 모바일의 할당은 Failed 카드의 다시 맡기기와 이어서 맡기기뿐이고, 새 티켓 할당과 Queued 런 옮기기는 하지 않는다(M38).
- **기술(M4).** Expo(React Native). iOS를 먼저 내고 Android는 나중이다.
- **서버 인증(M2).** 기기 토큰과 QR 연결(ADR 0015).
- **공개 API(M6).** 새 순수 패키지 `packages/api`에 계약을 두고 `/api/v1`로 연다. 지금 웹이 쓰는 서버 함수는 그대로 두고, 모바일에 필요한 것만 v1에 연다. 티켓 0103의 알림 사건 SSE도 `/api/v1` 아래에 두고 데스크톱과 모바일이 함께 쓴다. 데스크톱도 기기 토큰으로 인증하고, 같은 기계·원격 모두 첫 연결 때 자동 등록한다(M39). 화면 갱신용 변경 기록 SSE도 v1 아래에 기기 토큰 인증으로 연다(M26).
- **푸시(M10~M16).** Expo Push로 알림 사건 번호만 보낸다(ADR 0016).
- **모바일 디자인 시스템(M20).** 웹의 `packages/ui`와 따로 둔다.

제외:

- 온보딩, 러너 등록·고치기, ssh 대상 바꾸기, 비밀 값 저장(트래커 키, GitHub 토큰), MCP 쓰기 허용, Mapping 편집, Stats 세부 표(research 0014 6절과 같은 이유: ssh와 비밀 값은 ADR 0013이 MCP에서 막은 이유와 같다).
- 런 멈추기(M24, 나중). 재개만 한다.
- 기다리지 않고 시작, 에이전트에게 보내기(M28).
- Face ID 확인과 목록 스와이프 동작(M8, 나중에 정한다).
- 알림 안에서 바로 답 보내기(M16).
- ntfy 같은 외부 알림 연동(M17).
- Android(M4, 나중).

## 4. 화면

시안 MB1(2026-11-19 운영자 승인)을 옮긴다. 세로 한 손 쓰기를 기준으로 한다.

- **Dashboard(M18).** 웹 Dashboard와 같은 줄기로, 칸반 세 칸을 위쪽 세그먼트 Queued · Running · Done으로 바꿔 한 번에 한 칸을 보인다. 처음 열면 처리할 일이 있는 칸부터 보인다. 처리할 일은 웹과 같이 카드 위 꼬리표(Question, Permission, Human Check, Failed, Disconnected, 그리고 무엇을 기다리는지 아직 읽지 못한 런의 Waiting for Input)로 보이고, 꼬리표 카드가 칸 맨 위에 온다. Human Check는 Running 칸 맨 위에 "확인해 주세요"로 Question과 따로 묶는다(ADR [0023](../adr/0023-human-check-request.md)). Done 칸의 꼬리표는 Failed뿐이다. 카드에서 바로 할 수 있는 행동 하나(Question "답하기", Human Check "확인하기", Permission 거절, Paused "재개하기")를 둔다. Failed 카드에는 다시 맡기기를 둔다(M38). 제목은 "Dashboard"이고 요약 문장은 웹과 같다(`apps/web/messages/ko/home.json`. 예: "처리할 일은 확인할 일 1개, 답할 질문 2개, 멈춘 런 1개예요.", 처리할 일이 없으면 "처리할 일은 없고, 진행 중인 런이 3개 있어요."). "처리할 일만" 스위치를 둔다. 스위치는 세그먼트 아래 칸 개수 줄의 오른쪽에 이름과 붙여 두고, 이름을 눌러도 바뀐다. 글이 길거나 글자가 크면 다음 줄로 내려간다. 기준은 티켓 단위 To do로, 웹 Dashboard·알림·배지와 같다(M30). 다만 지금 웹 To do는 이미 답했거나 아직 읽지 못한 Waiting for Input도 세고 알림 사건은 이들을 만들지 않아, Dashboard와 데스크톱 배지의 수가 다를 수 있다. 멈춘 기다림, 보고 없이 멈춘 Paused, PR CI 실패는 To do가 아니라 카드에 보이기만 한다(M29). 맨 위에는 Workspace 고르기, Runners 버튼, 설정이 있다. 아래 탭 막대는 두지 않는다.
- **세그먼트의 처리할 일 표시(M19).** 칸 이름에는 전체 수를 붙이지 않고, 처리할 일이 있는 칸에만 노란 배지로 그 수를 붙인다. 고른 칸의 런 수는 세그먼트 아래 줄에 처리할 일과 나머지로 나눠 쓴다(예: Running 칸 "처리할 일 2 · Running 1").
- **칸 이름(M21).** 세 번째 칸은 웹과 같이 Done이고, 운영자 시간대로 오늘을 포함한 최근 7일 동안 끝난 런을 보인다. Failed 꼬리표 런은 날짜와 상관없이 칸 맨 위에 남는다(티켓 [0163](../tickets/0163-dashboard-done-week.md), ADR 0010 0163 갱신).
- **Runners 버튼(M18).** 평소에는 회색 버튼이고, Runner Issue가 있으면 문제 러너 수를 빨간 배지로 붙인다. 세는 법은 웹 레일 Runners 점과 같다(사용량 한도 러너는 세지 않는다, GLOSSARY). 버튼 전체를 빨갛게 하지 않는다.
- **Queued 카드.** 기다리는 이유를 메타 줄에 쓴다(웹 Dashboard의 Queued 이유 문구와 같게). 이유는 9종이다(`packages/app/src/runs/model.ts`의 `QueuedReason`: `starting`, `behind`, `no-capacity`, `runner-offline`, `project-missing`, `assignment-blocked`, `usage-limit`, `blockers-waiting`, `blockers-stuck`). 선행 티켓을 기다리면 선행 티켓 칩을 보이고, 칩이 있는 카드의 아랫줄은 티켓 키 없이 원인만 말한다(티켓 [0183](../tickets/0183-dashboard-blocker-line.md)). 멈춘 기다림은 빨간 테두리로 보인다. 카드 메뉴 시트에 Linear에서 열기와 런 취소를 둔다. 시안 MB1에 있던 "다른 러너에 맡기기"는 Queued 런을 옮기는 서버 동작이 없어 뺐고, 모바일에서 Queued 런을 옮기지 않는다(M38).
- **카드 공통.** 모든 칸의 카드에 PR이 열려 있을 때의 PR 칩(CI 실패, 충돌, base보다 뒤처짐, 티켓 [0167](../tickets/0167-dashboard-pr-chips.md))을 웹과 같은 규칙으로 보인다. 취소를 요청했지만 아직 끝나지 않은 런은 "취소 중"을 함께 보인다.
- **Paused 카드.** Running 칸에 꼬리표 Paused와 멈춘 이유 한 줄(Ganger에서 멈춤, 러너에서 멈춤, 보고 없이 멈춤)을 보이고 "재개하기" 버튼을 둔다(M24). To do·알림·배지에는 넣지 않는다(티켓 [0118](../tickets/0118-run-pause-resume.md)·[0120](../tickets/0120-runner-agent-stop-detection.md)).
- **Done 칸.** 처리할 일 카드(Failed)를 위에, Succeeded·Canceled는 한 줄짜리 묶음 목록으로 아래에 둔다. PR 병합 여부는 결과가 아니라 PR 정보로 곁에 보인다(ADR [0022](../adr/0022-run-outcome-from-agent-report.md)).
- **답하기 시트.** 질문, 맥락 한 줄, 선택지, "직접 쓰기"(웹과 같은 낱말), 아래에 고정한 "보내면 되돌릴 수 없어요"와 "보내기". 선택지는 글뿐이고 따로 설명 칸이 없다(`packages/app/src/question.ts`의 `readQuestion`). 고르기만 해서는 보내지 않는다(ADR 0010 6번).
- **Human Check 시트(M22).** 답하기 시트와 같은 방식이다. 무엇을 확인할지(에이전트가 보낸 글과 링크), 덧붙일 말(선택), "확인했어요"와 "고쳐 주세요"를 둔다. 답을 보내면 런이 Running으로 돌아간다.
- **Runners.** 「문제」와 「러너」 두 구역이다(제목과 카드 사이 8, 구역 사이 24). 문제 구역은 문제 카드(Offline, GitHub 인증, 사용량 한도, 사용 중인 gh 계정의 로그인 만료. 사용량 한도도 Runner Issue다, M5)이고, 러너 구역은 러너별 자리, 공급자 사용량 막대, 「GitHub (gh)」 줄이다. gh 줄은 사용 중인 계정을 `{login} · {host}`로, 만료됐으면 빨간 `{login} · 로그인이 만료됐어요`로, 계정이 없으면 gh 없음·로그인 안 됨·읽지 못함을 보인다(티켓 [0205](../tickets/0205-runner-gh-account.md)·[0207](../tickets/0207-gh-account-diagnosis.md)·[0219](../tickets/0219-mobile-pr-state-and-gh-account.md)). 보기만 한다.
- **설정.** 연결한 서버와 연결 상태, 이 기기 연결 끊기, 알림 켜기, 알림이 Expo Push를 거친다는 안내, 앱 버전. 종류별 켜기는 데스크톱 알림 설정과 같은 5묶음(Question, Permission, Human Check, Failed·Disconnected, Runner Issue)이고(M47), 꺼진 종류는 서버가 보내지 않는다. Mac 앞 미루기는 스위치 없이 늘 한다(M40).
- **빈 상태.** 쉬는 마스코트와 "에이전트가 묻거나 멈추면 알려 줄게요." 마스코트는 브랜드 가이드가 허용한 곳(빈 상태, 로딩, 연결이 끊긴 화면 등)에만 쓰고 목록 행이나 상태 알약 옆에 두지 않는다.
- **모양(M20).** 둥글기는 카드 10, 버튼과 세그먼트 바깥 8, 세그먼트 안 6, 시트 16, 상태 알약 6이다. 글꼴은 브랜드 가이드대로 Pretendard다(M41). 토큰은 모바일에 따로 두고, 값이 브랜드 가이드·ADR 0010과 같은지 비교하는 시험을 둔다(M34). 노란색은 주 버튼, 선택, 처리할 일 배지에만 쓰고 상태 색으로 쓰지 않는다. 처리할 일 배지(M19)는 ADR 0010 5번의 강조색 용도 목록에 없고, 둥글기(카드 10)는 ADR 0010 10번(카드 12)과 다르다. 모바일 디자인 시스템 티켓에서 이 두 모바일 예외를 ADR 0010에 적는다.

## 6. 서버 API

- `/api/v1`만 기기 토큰을 요구한다(ADR 0015). 지금 웹 화면과 서버 함수, `/api/identity`, webhook은 바꾸지 않는다.
- 읽기: Dashboard 세 칸과 처리할 일, 런 상세(처리할 일 띠의 `runNextStep`, 요약, PR 구역, 질문과 선택지, Human Check 내용, 실패 이유), Runners, 설정에 필요한 서버 정보. 타임라인과 터미널은 열지 않아 `requestRunLog`도 v1에 없다(M37).
- 쓰기: 답하기, Human Check 답하기, Permission 거절, 런 취소, 재개. 지금 서버 함수(`answerQuestion`, `answerHumanCheck`, `denyPermission`, `cancelRun`, `controlRun`의 `resume`)와 같은 규칙을 쓴다. `controlRun`의 `pause`는 v1에 열지 않는다(M24). 다시 맡기기(`assignTicket`에 이전 런의 저장소·러너·에이전트)와 이어서 맡기기(`continueRunFrom`)를 연다(M38). 여러 티켓을 맡기는 `assignTickets`는 열지 않는다. `startRunWithoutWaiting`과 `sendAgentMessage`는 v1에 열지 않는다(M28).
- 같은 요청 한 번만(M25): v1의 모든 쓰기는 `requestId`(16~64자)가 필수다. 같은 런에 이미 성공한 ID와 같은 내용이 다시 오면 다시 처리하지 않고 그 성공으로 답한다. 예외가 둘이다. `controlRun` 요청이 뒤에 실패로 기록되면(러너에서 재개하지 못함) 같은 ID로 다시 처리하고, `continueRunFrom`은 이어 만든 런이 없어졌거나 시작하지 못하고 끝났으면 같은 ID로 다시 처리한다. 거절된 요청은 기록하지 않아 같은 ID로 다시 시도할 수 있다. 같은 ID에 내용이 다르면 거절한다. 이유 값은 `answerQuestion`·`answerHumanCheck`가 `already-answered`이고 그 밖의 쓰기는 `request-reused`다(티켓 [0156](../tickets/0156-dedupe-run-actions.md), `handleRunActionOnce`). `answerQuestion`, `answerHumanCheck`, `cancelRun`, `controlRun`, `continueRunFrom`에는 이 보호가 있고, 거절은 v1에서 더했다. 웹의 `denyPermission`, `assignTicket`에는 없다. 모바일의 다시 맡기기는 이전 런 ID를 키로 기존 `run_action_requests` 표에 기록하고 새 런 ID를 결과로 남겨, 새 마이그레이션 없이 같은 요청을 한 번만 처리한다(티켓 0111). 거절은 이유 값(예: `already-answered`, `not-found`, `resolved`)으로 돌려주고 앱이 그 이유를 문장으로 보인다. 앱의 `requestId`는 `expo-crypto`의 UUID이고, 응답을 잃은 쓰기는 같은 ID로 한 번 더 보낸다(M55).
- 알림 사건: 티켓 0103의 목록과 SSE를 `/api/v1` 아래에 두고 데스크톱과 모바일이 함께 쓴다(M6). 0103 구현은 목록과 SSE를 `/api/notification-events`(v1 밖, `request-guard`만 거침)에 두었고, 옛 `/api/attention`도 v0.4.0에 남아 있다. v1로 옮기고 데스크톱 인증을 붙이는 일은 티켓 0108이 한다. v1 경로는 `/api/v1/notification-events`이고, 옛 `/api/notification-events`와 `/api/attention`은 v0.6.0까지 두고 지운다(M42). v0.6.0에서 옛 경로와 데스크톱 앱이 그리로 돌아가는 동작을 지웠다(티켓 [0213](../tickets/0213-remove-legacy-notification-routes.md)). 0108 전까지 0104는 알림 사건 경로에 토큰을 요구하지 않는다. 지금 알림 사건 동기화는 이 경로들에 요청이 올 때만 돌아(`apps/web/src/notifications/server.ts`), 데스크톱 앱을 끄면 사건이 생기지 않는다. 0108이 worker가 클라이언트와 상관없이 주기적으로 동기화하게 바꾸고, worker가 Expo Push도 함께 보낸다(M43). worker는 서버가 깨어 있는 동안만 돌아, 로컬 모드 노트북이 잠든 동안에는 사건도 푸시도 없다. 사건 하나를 읽는 경로는 아직 없어 0108이 더하고, 앱의 NSE는 그 경로로 사건 번호 하나의 제목과 대상을 읽는다.
- 화면 갱신(M26): 변경 기록 SSE(ADR [0019](../adr/0019-query-cache-and-change-events.md), 웹은 `/api/change-events/stream`)를 v1 아래에 기기 토큰 인증으로 연다. 앱이 앞에 있을 때만 붙고, 실패하면 폴링한다.
- 버전 호환(M27, M53): v1 응답 `meta`에 서버 버전, 계약 버전 `contractVersion`(N), 받아 주는 가장 오래된 앱 계약 `minClientContractVersion`(M)을 싣는다. 앱은 자기 계약 `APP_CONTRACT_VERSION`(K)과 필요로 하는 최소 서버 계약 `MIN_SERVER_CONTRACT_VERSION`(S)을 갖고, N ≥ S 이고 K ≥ M 이면 호환이다(`packages/api`의 `contractFit`). `/api/build`(티켓 [0180](../tickets/0180-stale-client-reload.md))는 웹 전용이라 앱이 쓰지 않는다.
- 계약을 바꿀 때: 필드·enum 값·경로를 더하면 `CONTRACT_VERSION`(N)만 올린다. 필드를 빼거나 뜻을 바꾸면 `MIN_CLIENT_CONTRACT_VERSION`(M)도 그 새 N으로 올린다. 앱이 새 서버 기능 없이는 동작하지 못하면 `MIN_SERVER_CONTRACT_VERSION`(S)을 그 기능이 들어간 N으로 올린다. 범위 규칙을 처음 넣은 지금은 N·M·K·S 모두 1이다. 이 규칙 전 앱은 계약이 정확히 1이어야 하므로, 그 앱이 남아 있는 동안 N을 올리면 그 앱은 막힌다. `minClientContractVersion`이 없는 응답은 M=1로 읽는다.
- 모르는 값(M54): 서버는 `packages/api`의 엄격한 스키마로 응답을 만들고, 앱은 같은 패키지의 `app*` 스키마로 읽는다. 앱은 모르는 필드를 버리고 모르는 상태·종류 값을 `unknown`으로 읽어 "알 수 없는 상태"로 보인다. 아는 상태인데 필요한 필드가 없으면 `unknown`으로 숨기지 않고 맞지 않는 서버로 다룬다.
- Host 거절: 다른 기기에서 열 주소가 허용되지 않으면 서버는 403으로 거절한다(티켓 [0157](../tickets/0157-address-webhook-setup.md) F7·F8). 응답 본문에는 읽을 수 있는 이유 값이 없으므로, 앱은 데스크톱 앱처럼 Host 검사를 받지 않는 `/api/identity`의 `webAccess`가 `host-not-allowed`인지 보고 인증 실패와 가른 뒤, 서버 맥의 Settings › 주소를 고치라고 안내한다.
- 새 낱말(기기 토큰, 기기 연결, 연결 코드)은 구현 티켓에서 GLOSSARY에 더한다. 러너 등록의 _Avoid_인 "페어링 코드"는 쓰지 않는다.
- 외부 입력(요청 본문, Expo 응답)은 경계에서 zod로 파싱한다(AGENTS.md).

## 7. 푸시

ADR 0016을 요약한다.

- Expo Push로 보낸다(M10). 서버는 보낼 곳 주소 하나만 알아, 나중에 직접 만든 중계로 바꿀 수 있다.
- 기기 연결 때 알림을 받을지 묻고, 허용한 기기에만 보낸다. 기기를 지우면 멈춘다(M11).
- Expo의 Enhanced Push Security는 끈다(M12).
- 알림에는 사건 번호, 받을 기기의 ID(무작위 UUID, 다른 서버의 같은 번호와 가른다), 티켓 내용이 없는 고정 문구("처리할 일이 생겼어요")만 싣는다. 폰의 NSE가 다른 기기에서 열 주소로 서버에 물어 제목과 내용을 채운다. 서버에 닿지 않으면 고정 문구가 그대로 보인다(M13).
- 종류는 지금 알림 사건 8종 그대로다(M29, `packages/app/src/notifications/causes.ts`: `question`, `human-check`, `permission`, `disconnected`, `failed`, `runner-offline`, `runner-auth`, `runner-usage-limit`). 모두 소리 있는 보통 알림이다. Human Check도 데스크톱의 지금 동작처럼 소리가 있고, 데스크톱은 Question·Permission·Human Check를 10분 뒤 한 번 더 알린다(M23). 모바일도 같게 10분 뒤 한 번 다시 알리고, To do 종류가 5초 안에 3개를 넘으면 묶으며(Runner Issue는 묶지 않는다), 다른 곳에서 처리된 사건의 알림은 조용한 푸시로 지운다(M33). 종류별로 끈 알림은 서버가 보내지 않는다(M40). Succeeded와 Canceled, Paused, Queued·Running으로 옮김은 알리지 않는다. 시간 민감(Time Sensitive) 알림은 쓰지 않는다(M14).
- 데스크톱 앱이 시스템 유휴 시간 기준 마지막 사용 시각을 1분마다 서버에 보고한다. 최근 2분 안에 사용했으면 Mac 앞으로 보고 모바일 푸시를 5분 미루며, 그 사이 해결되면 보내지 않는다(M15, M32). 10분 뒤 다시 알림도 같은 규칙으로 미룬다(M52). 이 미루기에는 스위치를 두지 않는다(M40).
- Question 알림에는 "답하기", Human Check 알림에는 "확인하기" 버튼 하나를 두고, 누르면 앱이 열려 그 시트가 뜬다. 다른 종류의 알림에는 버튼을 두지 않는다(M16, M22).

## 8. 보안

- 폰을 잃어버리면 그 기기의 토큰으로 런에 답하거나 취소할 수 있다. 기기 목록에서 지우면 `/api/v1`은 막힌다(ADR 0015). 웹 화면과 서버 함수는 인증이 없어, 그 기기가 서버의 다른 기기에서 열 주소에 닿는 네트워크(Tailscale을 쓰면 tailnet, 리버스 프록시나 터널이면 그 주소에 닿는 모든 곳)에서 빠지기 전까지는 브라우저로 여전히 답하고 취소할 수 있고, 웹의 기기 연결 화면에서 새 토큰을 받을 수도 있다. 웹 인증은 모바일 범위 밖이고 지금처럼 네트워크 경계와 Host 검사에 맡긴다(M36).
- 토큰은 서버에 해시만 두고 만료하지 않아, 기기 목록에서 지워야 끊긴다(M35). 기기 연결 QR의 코드는 짧게 살고 한 번만 쓴다.
- 데스크톱의 첫 연결 자동 등록(M39)은 연결 코드 없이 토큰을 내준다. 그래서 서버 주소에 닿는 기기는 토큰을 얻을 수 있다(웹 화면이 인증 없이 열리는 M36과 같은 경계다). 자동 등록은 저장한 기기 토큰이 없을 때(처음)만 한다. 토큰이 있는데 거절되면(지운 뒤) 조용히 다시 등록하지 않고 "다시 연결" 안내를 띄워, 사용자가 눌러야 다시 등록한다(M48).
- 푸시 내용은 사건 번호만 담겨 티켓 제목은 Expo와 Apple을 지나가지 않는다. 기기의 Expo 푸시 주소는 보낼 때마다 Expo를 지나간다. 주소가 새어 나가면 누구든 그 기기에 아무 문구나 Ganger 앱 이름으로 띄울 수 있다(ADR 0016). 다시 연결해도 주소가 바뀐다고 보장할 수 없으므로(열린 질문 14), Expo 푸시 주소는 어느 화면과 API 응답에도 싣지 않는다.
- 모바일에서는 비밀 값과 ssh 설정을 다루지 않는다(2절 제외).

## 9. 배포

- 데스크톱 앱 서명에 쓰는 Apple 개발자 팀으로 iOS 앱을 낸다(M7).
- App Store 심사관은 운영자 서버에 붙을 수 없으므로 앱 안 데모 모드(가짜 데이터)를 둔다(M7). 제품 앱은 `demo/`를 import 하지 않는다(AGENTS.md, 티켓 0047). 데모 데이터는 `apps/mobile/src/demo/`에 두고 모양은 `packages/api` 계약 타입에 맞춘다(M44).
- 개발 환경(M45): `pnpm dev:mobile` 하나로 시드된 데모 서버(`demo/`의 dev 서버)와 Expo 개발 서버를 함께 띄운다. 앱은 개발 빌드에서 QR 없이 그 로컬 서버에 자동 연결하고, 개발용 기기 토큰은 dev 서버가 발급한다. 개발 연결 정보는 데스크톱의 `GANGER_DESKTOP_DEV_SERVER`처럼 환경 변수로 받아 제품 앱이 `demo/`를 import 하지 않게 한다. 서버 없는 앱 안 데모 모드도 그대로 둔다. 시뮬레이터는 `127.0.0.1`의 평문 http dev 서버에 붙고, 개발 빌드에만 `NSAllowsLocalNetworking` ATS 예외를 둔다. 실기기 개발 빌드는 tailnet HTTPS(`tailscale serve`)로 붙어 예외가 필요 없다. LAN IP + http는 쓰지 않는다(M46).
- 서버는 HTTPS 주소로 닿아야 한다. iOS의 ATS는 기본으로 평문 http를 막고, 출시 빌드에는 예외를 두지 않는다(research 0014 3절, ADR 0015, M46).
- CI: 디자인 시스템 lint와 `check:lengths`는 `apps/web`만 본다. 색 검사(`check:colors`)의 허용 경로는 `packages/ui` 하나라, 모바일 토큰 위치를 더해야 한다(티켓 0105). `bundle`과 `smoke:bundle`의 서버 배포물에는 모바일 앱이 들어가면 안 된다.
- 출시: 브랜치 흐름은 ADR [0017](../adr/0017-develop-branch-flow.md)을 따른다. `.github/workflows/release.yml`은 `v*` 태그로 돌고 서명 비밀 값은 `release` environment에 있다. 버전 파일은 루트와 `apps/desktop`의 `package.json`이다(`scripts/release-version.ts`). 모바일 버전과 배포를 여기에 묶을지는 티켓 0112에서 정한다.

## 10. 순서

M9로 정한 순서다. 1번은 이 문서와 함께 들어가고, 2번부터는 티켓 0103이 머지된 뒤(2026-11-19 머지) 시작한다. 티켓은 세로 조각으로 나눠, 모바일 디자인 시스템과 앱 뼈대(0105)는 데모 모드로 서버 일과 나란히 먼저 시작하고, 쓰기 API는 쓰기 화면과 한 티켓(0107)에 묶었다(2026-11-19 운영자 확인).

1. ADR 0015·0016(이 문서와 함께)
2. `packages/api`와 읽기 API
3. 쓰기 API
4. 모바일 시안 확정과 모바일 디자인 시스템
5. Expo 앱 뼈대(데모 모드 포함)
6. Dashboard·답하기 등 쓰기 화면
7. 푸시

1~3은 모바일이 없어도 쓸모가 있다(다른 기기 클라이언트의 바탕).
